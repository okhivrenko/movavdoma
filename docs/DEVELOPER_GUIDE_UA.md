# Посібник з ручної розробки

Цей документ — стартова точка для розробника, який працює з MovaYakVDoma без
AI-агента. Він описує, де шукати код, куди додавати новий код і коли змінювати
архітектуру.

## Як влаштований застосунок

```text
Telegram / Cron / HTTP
          │
          ▼
      worker.js                 приймає update, перевіряє його та маршрутизує
          │
   ┌──────┼───────────────┐
   ▼      ▼               ▼
features/ domain/       platform/
сценарії  правила        зовнішні API
   │        │               │
   └────────┴─────── D1 ────┘
```

`worker.js` — єдина точка входу Cloudflare Worker. У ньому мають лишатися
HTTP/webhook, перевірка приватного чату, ідемпотентність Telegram update та
складання залежностей. Не переносити сюди бізнес-логіку нової функції.

| Місце | Що там лежить | Приклади |
| --- | --- | --- |
| `src/domain/` | чисті правила, формати, константи; без мережі, D1 та `env` | квоти, мовні напрямки, тексти |
| `src/platform/` | адаптери до зовнішніх сервісів | Telegram, OpenAI, Monobank |
| `src/features/<feature>/` | завершені сценарії продукту, D1-запити й Telegram UI | `vocabulary`, `daily-words`, `donations`, `admin`, `feedback` |
| `*.test.js` поруч із модулем | Node-тести за власником модуля | `src/features/daily-words/daily-words.test.js` |
| `test-support/` | спільні test helpers, які не запускаються як тести | `worker-test-helpers.js` |
| `migrations/` | послідовні, незмінні зміни схеми D1 | `0016_*.sql` — наступна міграція |
| `docs/adr/` | короткі записи важливих архітектурних рішень | модулі, доступи, багатомовність |
| `workflows/` | повторюваний процес виконання змін | feature/refactor/migration workflow |

Повна карта і межі залежностей: [ARCHITECTURE.md](./ARCHITECTURE.md).

## Куди додавати нову функцію

1. Визначити продуктову область. Наприклад, нова логіка карток —
   `src/features/vocabulary/`, оплати — `src/features/donations/`.
2. Винести обчислення без I/O у `src/domain/` і відразу покрити unit-тестом.
3. Зовнішній HTTP-клієнт або інтеграцію додати/розширити у `src/platform/`.
4. У feature-модулі реалізувати сценарій через явні параметри залежностей;
   не створювати приховані глобальні singleton-и.
5. Підключити сценарій у `worker.js` лише через імпорт і маршрутизацію.
6. Додати тест модуля поруч із ним; якщо змінено webhook/auth/головну
   маршрутизацію — також `worker.test.js`.

Під час роботи з D1 кожен запит має бути параметризований через `.bind()`, а
кожне читання або оновлення даних користувача — обмежене його Telegram user ID.
Callback має перевірятися так само: не довіряти `callback_data` і не діяти з
даними іншого користувача.

## Як додати базу даних або змінити контракт

Міграції — тільки forward-only. Не редагувати наявний файл, якщо він міг уже
потрапити в production. Додати наступний номер у `migrations/`, наприклад
`0016_add_translation_directions.sql`, і перевірити його локально:

```bash
npm run check:migrations
```

Перед production-міграцією та після неї перевірити журнал D1 через
`wrangler d1 migrations list <database> --remote`. Застосовувати файл тільки
через `wrangler d1 migrations apply <database> --remote`; не виконувати SQL із
`migrations/` напряму, інакше журнал міграцій втратить синхронність.

Якщо код уже читає нову колонку, спочатку застосувати міграцію, а лише потім
деплоїти Worker.

## Правила, які не можна ламати

- Працюємо лише з приватними Telegram-чатами.
- Секрети лишаються в Cloudflare Secrets і локальному `.dev.vars`; їх не можна
  друкувати, комітити чи замінювати.
- Словникова картка містить одне обране значення та рівно два приклади.
- Постійний рівень доступу не зменшується тимчасовим донатним доступом.
- `INTERFACE_VERSION` у `worker.js` змінюється лише за зміни постійних кнопок
  reply keyboard.

Продуктові деталі й актуальна схема: [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md).

## Багатомовність: як додавати правильно

Зараз працює English → Ukrainian. Каталог майбутніх напрямків лежить у
`src/domain/languages.js`, але сам по собі він не вмикає переклад.

Новий напрямок — це один цілісний реліз: нейтральна схема source/target мов,
backfill старих українських даних, вибір напрямку у профілі користувача,
валідація callback і SQL, direction-aware OpenAI prompt та рендеринг карток,
тести нового й legacy-сценаріїв. Поля `translation_uk` і `sentence_uk` —
legacy; їх не можна використовувати для іншої мови.

## Як масштабувати без передчасної складності

Поточна схема — один Cloudflare Worker + D1 — правильна, доки webhook-запити,
cron-задачі та обробка донатів укладаються в ліміти Worker і виконуються
швидко. Спочатку масштабувати всередині наявної структури:

1. Створити або розширити feature-модуль, а не новий сервіс.
2. Додати індекс через міграцію, якщо D1-запит став гарячим або зростає таблиця.
3. Винести довгу чи повторювану фонову роботу в Cloudflare Queue/Workflow лише
   коли потрібні гарантовані повтори, буферизація навантаження або робота не
   вміщується в один запуск Worker.
4. Додавати Durable Object тільки для справді спільного стану/координації,
   який не можна коректно вести в D1.
5. Відокремлювати сервіс або публічний API лише коли з'являються незалежні
   команди, власний життєвий цикл або окремі вимоги до доступу/масштабування.

Не потрібно додавати Express. Worker уже має `fetch`/`Response`; Hono варто
розглядати лише якщо з'явиться декілька версій публічного HTTP API зі спільним
middleware. Для Telegram webhook це зараз зайве.

## Робочий цикл розробника

Перед зміною прочитати `AGENTS.md`, цей посібник, відповідний feature-модуль,
його тести та [cloudflare-telegram-feature.md](../workflows/cloudflare-telegram-feature.md).

Після завершення маленького вертикального зрізу:

```bash
npm run check
git diff --check
```

Оновити `PROJECT_CONTEXT.md` для зміни поведінки або схеми, ADR — для
довготривалого архітектурного рішення, `IMPLEMENTATION_STATUS.md` — лише після
завершеного зрізу. Для поведінкових, конфігураційних або production-data змін
виконати реліз за [RELEASING.md](../RELEASING.md); для документації деплой не
потрібен.
